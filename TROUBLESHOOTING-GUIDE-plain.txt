======================
dsh-llm-proxy 排查指南
======================
（纯文本版 · 可直接转发到微信/QQ/邮件）

说明：本指南不预设你的任何配置。代理地址、端口、供应商、模型、API Key
一律以你本机实际配置为准，排查的第一步永远是"读取你的实际配置"。


────────────────────────
一、使用者快速自检清单
────────────────────────

插件"不能用"（对话超时 / 不走代理 / 设置卡不显示 / 测试连接失败等）时，
按顺序自检，卡在哪一步就对照后面的"常见症状对照表"。

[1] 确认插件已安装
    dsh plugin --profile web list
    输出中应包含 @superfish058/dsh-llm-proxy。没有则先安装：
    dsh plugin --profile web add @superfish058/dsh-llm-proxy

[2] 确认已重启 dsh web
    安装后必须"退出 DSH 托盘 → 重新启动"。仅刷新网页无效。
    重启后日志应出现：
      dsh-llm-proxy: engine=official|bundled ...（决定走哪条链路）
      随后：official policy installed / global dispatcher → RoutingDispatcher
      (proxy=<你的host>:<你的port>, proxiedHosts=[...])

[3] 确认设置卡正常显示
    设置 → 插件 → 可配置插件 → 模型代理，应看到完整配置表单。

[4] 读取你的实际代理地址，并用它测连通
    打开设置卡（或 ~/.dsh/settings.yaml 的 llm-proxy: 节），记下你实际
    配置的 proxyHost 和 proxyPort（这是你自己配的，可能是任何端口，
    别用网上的默认值猜）。然后用这个地址测试：
      # 把 <HOST> 和 <PORT> 换成你配置里的实际值
      curl -x http://<HOST>:<PORT> -s -o /dev/null -w "%{http_code}" https://www.google.com
    返回 200 = 代理可用；返回 000/超时/连接拒绝 = 代理没运行、端口不对、
    或代理软件没在监听。

[5] 确认模型已勾选并保存
    在设置卡"走代理的模型"列表里勾选要走的模型（列表来自你本机的
    供应商与模型配置），然后点击保存。
    注意：「测试连接」读的是已保存的配置，改勾选后必须先保存再测试。

[6] 用「测试连接」按钮验证
    每行模型右侧有「测试连接」按钮，点击后：
      - 成功：200 · 38ms · 经代理 · 多模态已开启
      - 失败：直接显示具体原因（认证失败、超时、限流、404 等）

[7] 真实对话测试
    选一个已勾选的模型发一条消息；是否真的走了代理，可在你自己的
    代理软件日志里确认。


────────────────────────
二、给对面大模型的排查任务书
────────────────────────
（完整版见单独文件：TROUBLESHOOTING-PROMPT.txt，可整段复制粘贴）

核心思路：让 DSH 里另一个有工具权限的大模型按 8 步自主排查——
  1. 读取实际配置（node/dsh 版本 + settings.yaml 的 llm-proxy 节 +
     实际 providers，不预设任何端口/供应商）
  2. 插件安装状态（dsh plugin list + bundle 注入检查）
  3. dsh web 日志（global dispatcher 行、proxy= 是否等于实际配置、
     proxiedHosts 是否非空）
  4. 代理连通性（用实际代理地址 curl 外网 vs 直连，对比判断）
  5. 模型与路由核对（key = <providerId>/<modelId>，与设置卡列表一致）
  6. API Key 验证（apiKey / apiKeyEnv / .credentials.yaml，只判存在非空）
  7. 设置页功能（设置卡是否显示、测试连接结果）
  8. 版本兼容性核对（DSH vs 插件版本、Node>=24，只核对不预设）
然后输出一份含全部字段的 JSON 报告（环境/实际配置/插件状态/每步检查
记录/代理连通性/API Key 状态/根因判断/修复方案/复验建议）。

────────────────────────
四、成果验收清单
────────────────────────

收到排查大模型的报告后，确认包含全部内容：
  [ ] 环境信息：操作系统、Node 版本、DSH 版本、插件版本
  [ ] 实际配置：从你机器读出的 proxyHost/proxyPort、proxiedModels、
      multimodalModels、retries、实际 providers（而非任何默认值）
  [ ] 插件安装与设置卡状态
  [ ] 日志核查：global dispatcher 行、proxy= 是否等于实际配置、
      proxiedHosts 是否非空
  [ ] 每步检查记录：命令、实际输出、结论
  [ ] 代理连通性：经代理 vs 直连的对比结果
  [ ] API Key 状态：按 provider 列出
  [ ] 根因判断 + 修复方案（可执行、按顺序）+ 复验建议

缺任何一项，可让排查大模型补充。


────────────────────────
五、修复后如何复验
────────────────────────

1. 重启 dsh web（退出托盘重新启动）
2. 看日志：global dispatcher 行的 proxy= 等于你的实际配置，
   且 proxiedHosts 非空
3. 测试连接：设置页点「测试连接」，确认 ✅ 连接成功
4. 对话测试：选走代理的模型发消息，正常响应
5. 代理日志确认：在你自己的代理软件日志里确认流量经过


────────────────────────
附：关于"模型 key"的说明
────────────────────────

- proxiedModels 里的 key 必须是 <providerId>/<modelId>
- providerId 是这台机器 llm-pi-ai.providers 里实际存在的 provider ID
  （每个人可能不同）
- 最稳妥：直接复制设置卡"走代理的模型"下拉列表里的值，不要自己拼
- 一个 key 命中后，该模型 baseURL 的域名会进 proxiedHosts；同一域名
  下的其他模型随之一起走代理（按 API 地址整组生效）
